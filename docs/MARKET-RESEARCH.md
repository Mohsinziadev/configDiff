## Answers to the competitive questions

1. **Done well already:** runtime validation (envalid, T3 Env, env-schema); `.env` vs `.env.example` drift and codebase usage scanning (dotenv-diff, which is thorough and actively released: modified 2026-10-20); encryption at rest (dotenvx); generic object diffing (microdiff).
2. **Still needs several tools or scripts:** comparing _nested_ JSON/YAML/TOML config across environments _with_ policy (e.g. "prod URL must not contain `staging`", "auth must not flip to false") and _safe-to-publish_ output. Generic diff libs have no policy or redaction; env tools have no nested formats.
3. **Underserved:** YAML/TOML/JSON app config compared across environments in CI; reports that are safe to paste into CI logs and PR comments.
4. **Realistically detectable locally:** missing/empty required keys, type changes, secret-shaped keys exposed under public prefixes (`NEXT_PUBLIC_*`), credentials embedded in URLs, an environment name leaking into another environment's values, the _same_ secret reused across environments, forbidden values, schema violations. Not detectable: whether a value is actually valid, reachable, or secret.
5. **Too expensive/risky for v0.1:** executing JS/TS config (unsafe), live infrastructure/cloud drift (needs credentials), semantic "impact" prediction, scanning source code for usage (dotenv-diff does this), secret entropy scanning (high false-positive rate; dedicated scanners exist), JSON Schema (large surface; Standard Schema covers the popular validators).
6. **Smallest useful product:** structural compare for env/JSON/YAML/TOML + a handful of explainable rules + redaction-by-construction + JSON report + CI exit codes.
7. **Measurable advantage over a plain diff:** reproducible fixtures in `tests/` show cases a text diff cannot express (reordered keys, array order policy, type changes, redaction, per-path severity). Performance is _not_ claimed as an advantage (see BENCHMARKS.md).

## Features not to duplicate

Codebase scanning for env usage, `.gitignore` checks, auto-fixing files, encryption, runtime `process.env` validation.

## Differentiators worth validating

- Nested structural comparison across env/JSON/YAML/TOML with one policy.
- Redaction as a data-model property (public report objects never contain sensitive raw values).
- Cross-environment rules (`environment-mismatch`, `sensitive-value-shared`).
- Zero-account, offline, no telemetry.

## Adoption barriers

Strong incumbent for `.env` drift (dotenv-diff); teams already hold validation in app code (Zod/T3 Env); policy files are extra upkeep; trust must be earned on a new redaction implementation.
